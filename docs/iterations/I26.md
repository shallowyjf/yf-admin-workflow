# I26：权限模型简化——取消岗位概念

## 迭代目标

人员授权统一收敛为“用户—组织成员关系—角色”。岗位与角色在当前产品中表达了相同的职责语义，却只有角色真正承载 Permission 和 DataScope，双轨配置会造成管理员重复维护、候选人不一致和演示理解成本。本轮完整移除岗位，不采用仅隐藏页面的兼容方案。

原计划的“系统入口、项目参与组织、项目成员页面闭环”顺延为下一轮 P1 目标。

## 最终模型

```text
Tenant
  └─ Organization
       └─ UserOrganization（用户可加入多个组织）
            └─ Role（每个组织可配置不同角色）
                 ├─ Permission：能做什么
                 └─ DataScope：能看哪些组织数据

Application + Project + ProjectMember：继续叠加系统和项目数据边界
```

- 删除 `Position`、`UserOrganizationPosition` 领域模型及两张数据库表；
- 删除岗位 API、页面、权限编码、默认数据、导入导出字段和 IAM 审计写入口；
- 工作流候选类型由五类收敛为 `USER / ROLE / ORG / ORG_ROLE`；
- 原 `ORG_POSITION` JSON 规则在迁移时转换为等价的 `ORG_ROLE`；
- 用户详情只配置组织关系、主组织、成员状态和组织内角色；
- 工单系统、项目成员、应用入口和数据资源权限模型保持不变。

## 数据迁移

Alembic `0019_i26_remove_positions` 执行：

1. 将流程定义、运行任务和候选快照中的 `ORG_POSITION` 转换为 `ORG_ROLE`；
2. 按既有职责映射岗位编码到角色编码，例如 `DEPT_MANAGER → WORKORDER_MANAGER`、`SUPERVISOR → REVIEWER`；
3. 删除五个 `system:position:*` 权限及其角色授权、数据范围；
4. 删除 `sys_user_org_position` 与 `sys_position`。

降级只能恢复表结构和岗位权限字典，不能恢复已删除的岗位成员数据；执行生产迁移前必须备份。

## 回归设计

- 同一用户在不同组织可配置不同角色，切换活动组织后权限随之变化；
- `ORG_ROLE` 只解析目标组织内有效用户、有效成员关系和有效角色；
- 停用用户、组织、成员关系或角色后不再成为新任务候选人；
- 用户创建、成员关系替换、IAM 导入导出均不再接受或输出 `position_codes`；
- `/iam/positions`、`/api/positions` 返回 404，导航与页面无岗位入口；
- 空库迁移后岗位表不存在，降级到 I25 可恢复旧表结构；
- 标准工单创建、提交、派单、认领、处理、复核、关闭全流程保持通过；
- 监管人员能看到待复核任务，驳回后处理任务仍回到原处理组织。

## 人工验收

1. `admin` 登录权限中心，导航仅包含组织、用户、角色、权限和审计。
2. 打开用户详情，为同一用户选择两个组织并分别配置不同角色，页面不出现岗位字段。
3. 打开组织详情，直属成员仅展示该组织内角色。
4. `wangwu` 将工单派到抢修组织，拥有 `REPAIRER` 角色的 `lisi` 可见并认领。
5. `lisi` 处理后，拥有 `REVIEWER` 角色的 `regulator` 可见待复核任务并完成复核。
6. 直接访问历史岗位页面/API，确认返回 404。

## 完成标准

- 应用代码中不再引用岗位领域概念；
- 当前 ORM 元数据和 Head 数据库不再包含岗位表；
- 迁移、IAM、页面、候选解析、空库验收和工单全量回归通过；
- 当前需求、API、架构和演示文档均以“组织 + 角色”为唯一人员授权模型。
