# I08：状态机与任务动作

## 本轮目标

把工单状态规则集中到一个状态机中，并实现派单、认领、提交处理结果、复核和关闭。任务动作必须同时经过功能权限与 TaskAccess；认领必须使用数据库条件更新抵御并发竞争。

## 已实现

- `WorkOrderStateMachine` 集中维护 7 条合法状态迁移，非法迁移统一返回 409。
- `TaskAccessService` 独立判断候选人、当前办理人以及候选人/办理人联合访问。
- `POST /api/workorders/{id}/dispatch`：完成 `DISPATCH` 任务，按 `ORG_ROLE + REPAIRER` 创建处理任务。
- `POST /api/workorders/{id}/claim`：使用 `status=PENDING AND assignee_id IS NULL` 条件更新原子认领。
- `POST /api/workorders/{id}/result`：仅当前办理人可提交，完成处理任务并创建 `REVIEW` 任务。
- `POST /api/workorders/{id}/review`：支持 `APPROVE` 和 `REJECT`；退回时为原办理人创建已分配的处理任务。
- `POST /api/workorders/{id}/close`：完成态工单可由责任范围或所属组织范围内有关闭权限的用户关闭。
- “我的任务”在任务被认领后只对办理人显示，不再继续显示给其他候选人。
- 任务历史记录 `CREATE`、`CLAIM`、`COMPLETE`、`RETURN` 和退回后的 `ASSIGN`。

本轮没有数据库结构变化，因此不新增 Alembic Revision。

## 人工验收

1. `wangwu` 创建并提交工单，再派给“管网运行部”。
2. `lisi` 和 `zhaoliu` 均能在认领前看到处理候选任务。
3. `lisi` 认领后工单进入 `PROCESSING`，`zhaoliu` 的“我的任务”不再显示该任务，再次认领返回 409。
4. `zhaoliu` 提交处理结果返回 403；`lisi` 提交成功并进入 `PENDING_REVIEW`。
5. `wangwu` 可选择退回，确认 `lisi` 获得已分配的新处理任务；再次提交后可复核通过。
6. 复核通过后状态为 `COMPLETED`，关闭后状态为 `CLOSED`。

## 边界与实现说明

- 派单与关闭使用 DataScope；关闭同时允许当前责任组织和原所属组织范围，保证派出组织仍可完成闭环。
- 认领、处理和复核使用稳定 permission code 加当前任务 TaskAccess，TaskAccess 不替代功能权限。
- I09 才固化标准 DMA 单场景 E2E、完整业务时间线顺序和正式演示脚本；I08 不增加 Transfer 动作，也不提前制作 HTML UI。

### Decision Needed：任务动作与 SELF DataScope

通用授权伪代码要求任务动作同时经过 DataScope 和 TaskAccess，但 Seed 把维修人的 `claim` 配置为 `SELF`；认领前用户既不是创建人也不是办理人，因此严格套用工单 SELF 查询会让所有候选人无法认领。I08 按更具体的 API 校验表和 WF-001/WF-003 验收用例处理：认领、处理、复核采用“功能权限 + 当前任务 TaskAccess”，派单、查看和关闭仍独立执行 DataScope。没有修改 IAM 关系或 DataScope 枚举；正式版若要求四层校验同时成立，需要在后续设计中明确“候选任务对应工单”是否属于 SELF 范围。
